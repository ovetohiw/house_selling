## Стартовый воркфлоу

Единый порядок (анти-додумывание). Детали ролей — [.cursor/roles/index.md](.cursor/roles/index.md). Этап exec plan — только при роли `developer` и фазе `build`.

0. Синхронизация с remote (до чтения PROGRESS) — см. процедуру ниже. При hard на sync — стоп, работу не начинать.
1. [.cursor/PROGRESS.md](.cursor/PROGRESS.md) — блокер; `Текущая роль`; `Фаза пайплайна`; «Следующий лучший шаг» (непустой при активной фиче); mid-stage: **осталось**.
2. [.cursor/HANDOFF.md](.cursor/HANDOFF.md) — если заполнен: `to_role` = `Текущая роль` (или `none` при закрытом пайплайне). Рассинхрон → **hard**, роль не угадывать. Роль `N/A` → только bootstrap (analyst / `Пайплайн: spec`).
3. [.cursor/FEATURE.md](.cursor/FEATURE.md) — контракт; `Пайплайн:` согласован с фазой в PROGRESS; поле `Exec plan:`.
4. Файл роли `.cursor/roles/{role}.md` + Discipline в [.cursor/roles/index.md](.cursor/roles/index.md).
5. **Только если** роль `developer` **и** фаза `build` **и** HANDOFF не требует иной роли: при `Exec plan:` не «нет» — чеклист [.cursor/exec-plans/index.md](.cursor/exec-plans/index.md) (plan → только текущий этап). Иначе этап decompose **не** читать как задание.
6. [.cursor/PLANS.md](.cursor/PLANS.md) — только когда нужен **новый** план или меняется политика планов.
7. UI (роли analyst / developer по скоупу): [.cursor/refs/](.cursor/refs/README.md) → [.cursor/convention/UIDESIGN.md](.cursor/convention/UIDESIGN.md) + STACK. Домены — [.cursor/convention/index.md](.cursor/convention/index.md).
8. Последние коммиты: `git log --oneline -5`.

Горизонт сессии — **одна роль** (и при build+plan — один этап). После DoD роли: HANDOFF + PROGRESS → **стоп**. Соседнюю роль и соседний этап в том же прогоне не стартовать.

Если текущая базовая верификация падает — чините её. Новую работу при неисправном стартовом состоянии не начинайте.

### Синхронизация с remote (шаг 0)

1. Если нет git-репозитория — hard (блокер в PROGRESS).
2. Если remote / upstream текущей ветки **нет** — записать в PROGRESS «sync N/A, remote отсутствует» и продолжить старт (push в конце этапа станет hard, если remote так и не появился).
3. Иначе: `git fetch` (upstream текущей ветки).
4. `git status`: грязное дерево с локальными правками **до** начала работы этой сессии → hard (не затирать чужое); чистое — дальше.
5. Сравнение с upstream: **behind** → `git pull --ff-only`; **ahead** → ок; **diverged** или `pull --ff-only` не прошёл → hard; сбой fetch/pull (auth/network) → hard.
6. Запрещено: `pull` с merge «наугад», `reset --hard`, force-sync без явной просьбы человека.

## Автономный цикл исполнения

Горизонт одного прогона в фазе `build` — **только текущий этап** exec plan (или работа без плана в объёме FEATURE, эквивалентная одному этапу). Соседний этап в том же прогоне не начинать. Указатель «текущий шаг» в plan после закрытия этапа можно сдвинуть на следующий для handoff; исполнение следующего — следующая сессия или явный пинок.

```text
sync с remote (шаг 0)
 → старт (PROGRESS → HANDOFF → FEATURE → роль → [developer+build] plan/этап)
 → работа роли до DoD роли / hard
 → HANDOFF + PROGRESS → СТОП
 (внутри developer+build+plan: статус этапа в работе → … → DoD этапа → commit+push этапа → handoff роли/этапа → СТОП)
```

Канон статусов этапа (при `Exec plan:`): `в очереди` → `в работе` → `верификация` → `готово`. Plan «Текущий шаг».Статус и ровно один чекбокс текущего этапа в `*-decompose.md` всегда совпадают; расхождение = ошибка handoff.

Обязательные смены статуса **до** продолжения работы (не «в конце сессии, если вспомнил»):

| Момент | Действие |
|--------|----------|
| Старт текущего этапа | plan + decompose → `в работе`; снять `в очереди` |
| Начало прогона DoD этапа | оба → `верификация` |
| Зелёный DoD (перед commit) | оба → `готово`; поля DoD этапа заполнены |
| Hard mid-stage | **не** откатывать и **не** ставить `готово`; оставить текущий (`в работе` или `верификация`) + запись в лог plan и PROGRESS |

Правила цикла:

- Не ждать подтверждения на каждый шаг реализации внутри этапа.
- Не ставить этапу `готово` без полной схемы DoD этапа.
- Не оставлять текущий этап в `в очереди` после старта его исполнения.
- Fail проверки → чинить в рамках этапа; после **2 неудачных** попыток на одну и ту же ошибку → hard-блокер (третья «наугад» запрещена).
- Soft-решение → запись в «Открытые решения» / лог plan (и в PROGRESS, если влияет на handoff) → продолжить.
- При зелёном DoD этапа — обязательные commit и push по процедуре ниже (без отдельного запроса пользователя). Mid-stage и выход по hard — без авто commit/push.
- Гейты DoD фичи / completed / ranking **не ослаблять**.
- Лимит кругов verify↔build и accept↔build: ≤2 на один fail; далее hard ([.cursor/roles/index.md](.cursor/roles/index.md)).

### Commit и push по готовности этапа

Только после зелёного DoD этапа (поля схемы заполнены; этап можно ставить `готово`):

1. `git status` / `git diff` — в коммите только файлы этапа (код + plan/decompose + PROGRESS; FEATURE если трогали); нет секретов ([.cursor/convention/SECURITY.md](.cursor/convention/SECURITY.md)).
2. Сообщение коммита: одна цель — закрытие этапа `{id}` / краткий смысл DoD (why), не «WIP».
3. `git add` релевантных файлов → `git commit`.
4. `git push` (или `git push -u origin HEAD`, если upstream ещё нет).
5. В PROGRESS: ветка, short SHA, факт push (или «push не выполнен»).
6. СТОП (соседний этап не стартовать).

Запрещено: `--force` / `--force-with-lease`; `--no-verify`; amend уже запушенного; push чужой ветки; коммит красного DoD или mid-stage.

Провал commit (хук) или push → hard в PROGRESS; при успешном commit и упавшем push — зафиксировать SHA и «push не выполнен»; этап не считать доставленным на remote.

Работа без Exec plan («эквивалент одного этапа»): то же commit+push при закрытии этого объёма (после Build→Verify handoff — стоп роли developer).

### Soft vs hard

**Soft (решить и продолжить):** выбор реализации внутри контракта FEATURE и STACK; повтор уже принятого паттерна репозитория; уточнение из карты контекста / полей этапа «Читать» / «Менять»; точечный fix без расширения скоупа фичи, без которого DoD этапа не закрыть.

**Hard (стоп, блокер в PROGRESS, вопрос человеку — без тихого обхода):**

- нет git-репозитория; грязное дерево на входе сессии; diverged с upstream; сбой fetch / `pull --ff-only`;
- сбой commit или push при закрытии этапа;
- нужен выбор в STACK / архитектуре, которого нет;
- правка вне скоупа FEATURE или ломает зафиксированный контракт поведения;
- security-неоднозначность (секреты, доступ, обход защиты);
- нужны секреты / креды / действие человека вне репозитория;
- этап негоден к исполнению (пустые «Читать» / «Менять», однострочный этап);
- смена **смысла** этапа или цели plan (task/bug: запись + стоп; big-task: hot-fix только если не меняет смысл остальных этапов — иначе стоп);
- 2 неудачных фикса одной проверки;
- нарушение Role Discipline / неполный HANDOFF / hop `pass` при blockers;
- рассинхрон `Текущая роль` ↔ HANDOFF `to_role`; пустой «следующий шаг» при активной фиче;
- этап decompose при роли ≠ developer или фазе ≠ build; угадывание роли;
- >2 кругов verify↔build или accept↔build на один fail.

Детали ролей — [.cursor/roles/index.md](.cursor/roles/index.md). Детали старта по plan — [.cursor/exec-plans/index.md](.cursor/exec-plans/index.md).

## Тест работоспособности приложения

- Поднять приложение: `docker compose up --build` (локально без Docker: `npm run dev`)
- Прогнать тесты: `npm run lint` (unit/e2e раннеры появятся на следующих этапах)
- Верификация: `GET http://localhost:3000/api/health` → 200; открыть `http://localhost:3000/` — бренд, телефон в шапке, прибытие без витрины/карты/календаря/льгот

## Definition of Done

Канон готовности фичи. Доказательство — одна схема полей (критерий → команда/действие → результат → артефакт → дата/сессия). Шаблон заполнения — в [.cursor/FEATURE.md](.cursor/FEATURE.md) («Доказательства DoD»). Пустой или однословный блок («ок», «прогнано») готовность не подтверждает.

Уровни закрытия:

- этап exec plan — DoD этапа в `*-decompose.md` (объём этапа, не подмена DoD фичи);
- фича — пункты ниже + заполненные доказательства в FEATURE.md + закрытый пайплайн ролей;
- смысловая работа с планом — `*-result.md` (секция «Верификация» по той же схеме) + запись в [.cursor/exec-plans/ranking/](.cursor/exec-plans/ranking/index.md).

Фича готова, когда:

- каждый критерий приёмки в FEATURE отмечен и имеет строку доказательства по схеме выше;
- каждый отмеченный уровень верификации в FEATURE (unit / интеграция / сквозной / health-check / базовая из AGENTS) прогнан: команда и результат записаны;
- базовая верификация из слотов ниже зелёная, когда слоты заполнены; если слоты пусты — это зафиксировано в доказательствах, раннер не выдумывается;
- health-check / smoke — по слоту «Верификация» ниже или явной записи в FEATURE;
- доказательства записаны в FEATURE.md; для handoff сессии — кратко в PROGRESS.md;
- гейты G1–G8 ниже отмечены.

### Гейты

Все пункты обязательны. Пока любой не выполнен — статус `готово`, закрытие completed и нормальная запись в ranking **запрещены**.

- [ ] **G1.** Все критерии приёмки отмечены; у каждого заполнены все поля схемы (критерий, команда/действие, результат, артефакт, дата/сессия).
- [ ] **G2.** У каждого отмеченного уровня верификации заполнены все поля схемы (включая `Роль:`); результат не fail.
- [ ] **G3.** Если слоты «Тест работоспособности» выше заполнены — базовая верификация зелёная. Если слоты пусты — в доказательствах явно: «слоты пусты» и что проверено вместо этого (раннер не выдуман).
- [ ] **G4.** В PROGRESS нет открытого блокера по этой фиче, который отменяет заявленный прогон.
- [ ] **G5.** При `Exec plan:` не «нет» — все этапы до закрытия фичи в статусе `готово` с заполненным DoD этапа (либо фича явно снята / сужена с записью). При `Exec plan: нет` — N/A.
- [ ] **G6.** Пайплайн закрыт: фаза `accept` завершена; HANDOFF `verdict: pass`, `to_role: none`; нет блокера в PROGRESS, отменяющего прогон.
- [ ] **G7.** Каждый security must в FEATURE: доказательство по схеме или явный `N/A` + обоснование; should не блокируют.
- [ ] **G8.** Независимый verify: отмеченные уровни и/или базовая проверка при пустых слотах заполнены ролью **tester** (`Роль: tester`); Developer не единственный автор этих строк.

Чеклист гейтов дублируется в FEATURE.md («Доказательства DoD»); пустой чеклист = не готово.

### Не считается готовым

- только код / diff / «реализовано» без прогона;
- однословные «ок», «прогнано», «зелёное» без команды, результата и артефакта;
- команда или раннер, которых нет в AGENTS.md / STACK.md;
- подмена отмеченного сквозного / health-check юнитом на моках;
- отключение, skip или ослабление обязательных проверок ради зелёного без записи риска в PROGRESS;
- DoD этапа как доказательство готовности всей фичи;
- `готово` или перенос в completed при пустых / неполных полях схемы;
- оценка A или B в ranking при неполной «Верификации» в result (тогда максимум C — либо сначала добить доказательства);
- Accept / `готово` по одному `summary` HANDOFF без сверки каждого критерия;
- самозакрытие: одна сессия закрывает Build→Verify `pass` и Verify→Accept `pass` или заполняет за tester строки G8;
- hop `pass` при неполном HANDOFF или нарушении Role Discipline.

## Рабочие правила

- Работать над одной фичей за раз;
- Исполнение — по старту и циклу выше: sync; роль; soft решать и продолжить, hard — стоп; одна роль за сессию; при зелёном DoD этапа (developer) — commit+push, затем handoff и стоп;
- Не помечать фичу сделанной, если написан только код;
- Визуальные референсы — папка [.cursor/refs/](.cursor/refs/README.md) (пусто допустимо). Перед UI смотреть refs, UIDESIGN, STACK;
- Соблюдать доменные ограничения агента по [.cursor/convention/index.md](.cursor/convention/index.md) (канон темы — один файл; точечно SECURITY / UIDESIGN при секретах и UI);
- Соблюдать [.cursor/roles/index.md](.cursor/roles/index.md) (Discipline, conflicts, session-start).

## Окончание сессии

Обновляйте только то, что реально затронули:

- всегда: [.cursor/PROGRESS.md](.cursor/PROGRESS.md) — роль, фаза, сделано, **осталось** (если mid-stage), следующий шаг, round при hop; при смене роли — заполненный [.cursor/HANDOFF.md](.cursor/HANDOFF.md);
- если меняли контракт / статус / доказательства фичи: [.cursor/FEATURE.md](.cursor/FEATURE.md);
- если есть активный план: файлы в `.cursor/exec-plans/inprogress/...`;
- если **закрыли** смысловую работу: `.cursor/exec-plans/completed/` (`*-result.md` с «Оценкой качества» и следом пайплайна G6–G8) и [.cursor/exec-plans/ranking/](.cursor/exec-plans/ranking/index.md);
- [.cursor/STACK.md](.cursor/STACK.md) — только если изменился стэк;
- [.cursor/INDEX.md](.cursor/INDEX.md) — только если изменилась карта процессных документов;
- [README.md](README.md) — только если изменилось описание **продукта** (запуск, имя); не писать туда процесс, роли, DoD или карту `.cursor/`;
- при зелёном DoD этапа — commit+push по процедуре выше, затем handoff и стоп; mid-stage и hard — без авто commit/push;
- соседний этап и соседнюю роль в том же прогоне не стартовать;
- оставьте репозиторий в состоянии, из которого следующая сессия может продолжить по PROGRESS + HANDOFF без додумывания.
